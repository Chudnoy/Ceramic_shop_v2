# Журнал архитектурных решений

## Как читать

- **Принято** — на решение опирается текущий код.
- **Временно принято** — работает сейчас, но может быть пересмотрено.
- **Открыто** — решение ещё нельзя закладывать в схему.

## Принятые решения

### D-001. Модульный монолит

**Статус:** принято.

Один Flask-проект с отдельными route/service/database модулями соответствует масштабу и учебным целям.

### D-002. Application factory

**Статус:** принято.

`create_app(test_config)` используется для изоляции конфигурации и тестовой базы.

### D-003. Service владеет составной транзакцией

**Статус:** принято.

Database-функции принимают `conn`, а service выполняет commit/rollback.

### D-004. Условные переходы статусов

**Статус:** принято.

Переход выполняется через `WHERE status = expected_status`, а успех определяется `rowcount`.

### D-005. Состав заказа нормализован

**Статус:** принято.

`order_items` заменили JSON в `orders`.

### D-006. Исторический snapshot позиции

**Статус:** принято.

`product_name` и `unit_price` сохраняются в заказе. `product_id` nullable и использует `ON DELETE SET NULL`.

### D-007. Создание заказа резервирует работу

**Статус:** принято.

Создание заказа и `available → reserved` происходят одной транзакцией.

### D-008. Partial checkout требует явного согласия

**Статус:** принято.

Недоступные позиции остаются в корзине. Заказ из доступной части требует checkbox/значение подтверждения.

### D-009. Архив предшествует окончательному удалению

**Статус:** принято.

Публичное скрытие и необратимое удаление — разные действия.

### D-010. Собственный migration runner

**Статус:** принято для текущего проекта.

История `v001–v007`, журнал, отдельная транзакция на версию, неизменяемые исторические файлы.

### D-011. Seed отделён от миграций

**Статус:** принято.

Миграции строят структуру; seed добавляет демонстрационные записи.

### D-012. Локальная база не хранится в Git

**Статус:** принято.

`shop.db` и журналы игнорируются. Схема восстанавливается миграциями.

### D-013. Отзывы удалены

**Статус:** принято.

Функциональность не переносится искусственными create/drop миграциями: история удаления остаётся в Git.

## Временно принятые решения

### D-101. SQLite

Подходит локальной разработке и текущей нагрузке. Production-выбор будет сделан после определения платформы и торговой модели.

### D-102. Один `products`

Сохраняется до предметного решения. Нельзя путать временную техническую сущность с окончательной моделью сайта.

### D-103. Один основной `img`

Достаточно для текущего интерфейса, но будущая Work/Project модель, вероятно, потребует галерею.

### D-104. Один администратор через env

Приемлемо для разработки и раннего закрытого использования, недостаточно для зрелой эксплуатации.

### D-105. Локальное хранилище uploads

Работает локально, production-вариант зависит от хостинга.

## Открытые решения

### O-001. Project ↔ Work

- one-to-many;
- many-to-many;
- основной проект плюс дополнительные связи.

### O-002. Work ↔ Shop item

- магазин как подмножество Works;
- отдельный коммерческий слой;
- Shop item без Work.

### O-003. Уникальные и складские позиции

Нужны точные реальные примеры Полины.

### O-004. Публичная информационная архитектура

Нужно утвердить состав страниц и приоритет авторского высказывания против магазинной навигации.

### O-005. Production database

SQLite или PostgreSQL.

### O-006. Deployment platform

От неё зависят WSGI, persistent storage, backups, database и secrets.

### O-007. Оплата и доставка

Провайдеры и правила пока не определены.

### O-008. Доступ к заказу покупателем

Session token, подписанная ссылка, кабинет или только email.

### O-009. Изображения

Локальный persistent volume или object storage; форматы и производные размеры.

## Правило добавления решения

Запись должна содержать:

```text
контекст
решение
почему
последствия
статус
```

Открытый вопрос не объявляется решением только потому, что один вариант выглядит архитектурно красивее.
