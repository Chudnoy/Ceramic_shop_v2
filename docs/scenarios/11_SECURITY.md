# 11. Безопасность

## Переменные окружения

```env
SECRET_KEY=...
ADMIN_LOGIN=...
ADMIN_PASSWORD_HASH=...
```

`.env` не должен попадать в Git. `SECRET_KEY` должен быть длинным и случайным.

## Пароль администратора

Хранится хеш Werkzeug, а не пароль. Проверка выполняется через `check_password_hash()`.

## CSRF

Для session создаётся токен:

```python
secrets.token_urlsafe(32)
```

POST-формы отправляют скрытое поле, а общий `before_request` отклоняет запрос без совпадающего токена.

## Параметризованный SQL

Пользовательские значения передаются через `?`:

```python
conn.execute("SELECT * FROM products WHERE id = ?", (product_id,))
```

Динамические имена сортировки должны проходить белый список.

## Серверная валидация

HTML помогает интерфейсу, но сервер заново проверяет обязательные строки, email, числа, статусы, категории, теги, количество, доступность и допустимость перехода.

## Условные обновления

```sql
WHERE id = ? AND status = ?
```

защищает от устаревшей формы и конкурирующего изменения состояния.

## Персональные данные заказа

`/order_success/<order_id>` показывает имя, email, телефон, адрес и состав. UUID трудно подобрать, но ссылка остаётся ключом доступа.

Перед production нужно:

- привязать просмотр к session или подписанному временному токену;
- запретить индексацию;
- не логировать контакты;
- не коммитить рабочую SQLite-базу.

## Debug

`debug=True` допустим только локально.

## Загрузки

Следует проверять расширение, размер, безопасное случайное имя и отсутствие пользовательского пути. Позже можно добавить MIME-проверку и внешнее хранилище.
