# Известные ограничения и технический долг

Документ не является списком обвинений. Он показывает, какие свойства проекта уже надёжны, а какие ещё нельзя обещать пользователю.

## Приоритет A — блокирует предметное развитие

### 1. `product` смешивает Work и Shop item

Обязательные цена, год и описание формы делают сущность удобной для текущей витрины, но не для всех художественных случаев.

Нужно решить с Полиной:

- Projects и серии;
- работы без продажи;
- проданный публичный архив;
- уникальные и тиражные вещи;
- магазинная позиция без самостоятельной Work;
- связь Work ↔ Shop item.

### 2. Количество и уникальность

Корзина и `order_items` поддерживают `quantity > 1`, но `products.status` предполагает одну уникальную работу. Один заказ может сейчас запросить несколько единиц одной записи, хотя резервируется она одним status.

До production необходимо выбрать модель:

```text
уникальный объект
складская позиция
изготовление под заказ
небольшой тираж
```

и задать отдельные инварианты.

## Приоритет B — блокирует production

### 3. Development server и debug

`app.py` запускает `debug=True`. Нет production WSGI-конфигурации.

### 4. Инициализация при импорте

`init_db()` вызывается только в блоке `if __name__ == "__main__"`. При запуске через WSGI импорт `create_app` сам по себе не применит миграции.

Нужно выбрать явную deployment-команду миграций или startup hook, не допускающий одновременного запуска миграций несколькими workers.

### 5. SQLite

SQLite подходит текущей разработке, но production-решение зависит от:

- реального трафика;
- числа writers;
- хостинга;
- backup;
- необходимости нескольких процессов.

Переход на PostgreSQL не должен происходить «для солидности», но должен быть оценён до запуска магазина.

### 6. Изображения на локальном диске

Нет гарантии сохранности между deployments и несколькими instances. Нет resize, MIME-проверки, лимита размера и галереи.

### 7. Защита заказа

`order_success/<uuid>` доступен по ссылке без session-ownership.

### 8. Персональные данные

Не зафиксированы privacy policy, retention и процедура удаления/экспорта данных.

### 9. Админская авторизация

Один login/hash, без rate limit, ролей, 2FA и audit log.

### 10. Наблюдаемость

Нет структурированного logging, error tracking, health check и alerting.

## Приоритет C — качество и удобство

### 11. Каталог с тегом

При tag-фильтре category/search/sort не комбинируются с тегом.

### 12. Валидация email

Проверяется только наличие `@`.

### 13. Seed по `COUNT(*) == 0`

Частично удалённые стартовые данные не восстанавливаются и не синхронизируются.

### 14. Одно изображение

`products.img` поддерживает один главный файл. Нет порядка, alt-текста, detail-кадров и обложки проекта.

### 15. Отсутствует slug работы

Публичный URL использует UUID, а не человекочитаемый slug. Это не ошибка, но влияет на редакторский UX и SEO.

### 16. Нет пагинации

Каталог и административные списки загружают все подходящие записи.

### 17. Нет optimistic locking

Два открытых admin-окна могут перезаписать изменения друг друга.

### 18. Статистика упрощена

`total_revenue` суммирует все заказы, включая отменённые. Это скорее «общая сумма записанных заказов», а не финансовый показатель.

### 19. Код-стиль

Есть смешение табов и пробелов, длинные строки, устаревшие комментарии и docstring страницы работы, где ещё упоминаются отзывы. Ruff пока не подключён.

### 20. Мёртвые или спорные элементы

`product_exists()` остаётся в database-модуле без очевидного текущего использования. Такое удаляется только после поиска и тестов, а не механически.

## Уже устранено

- старый `create_schema()`;
- `ensure_product_columns()`;
- JSON-состав заказа;
- параллельные способы создания схемы;
- функциональность отзывов;
- использование локальной БД в тестах;
- хранение открытого admin-пароля;
- отсутствие CSRF;
- неатомарное создание заказа;
- изменение work status активного заказа без защиты.

## Как работать со списком

Каждый пункт при начале работы превращается в:

```text
наблюдаемое ограничение
→ требуемое поведение
→ архитектурное решение
→ небольшой этап
→ тесты
→ документация
```

Не нужно закрывать весь список перед следующим полезным изменением. Важно не выдавать незакрытый пункт за уже решённый.
